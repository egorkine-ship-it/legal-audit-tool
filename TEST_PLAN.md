# План тестирования legal-audit-tool

Цель плана — ловить ошибки, которые чаще всего ломают реальный аудит сайтов:
недоступные страницы, JS-подвалы, soft-404, неверно найденные документы,
галлюцинации LLM, зависающие проверки, плохой PDF и потерю истории после
перезапуска.

## Быстрый запуск проверок

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest tests/ -q
.venv/bin/python scripts/run_acceptance.py
```

Для полного acceptance-прогона:

```bash
.venv/bin/python scripts/run_acceptance.py --full
```

Если нужно тестировать настоящий Playwright-рендеринг:

```bash
.venv/bin/python -m playwright install chromium
```

## 1. Smoke-проверка проекта

Проверяем до каждого деплоя:

- все ключевые модули импортируются;
- YAML-конфиги читаются;
- приложение стартует без синтаксических ошибок;
- базовый pytest-набор зелёный.

Команды:

```bash
.venv/bin/python scripts/run_acceptance.py
.venv/bin/python -m pytest tests/ -q
```

## 2. Авторизация и секреты

Проверить вручную и автотестами:

- без логина приложение не показывает Dashboard, историю, настройки и отчёты;
- `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `SESSION_SECRET` заданы в env;
- дефолтный `SESSION_SECRET=change-me` не используется в production;
- logout очищает сессию;
- перезагрузка страницы не выбрасывает пользователя при валидной сессии;
- неверный или поддельный `auth`-token не логинит пользователя.

## 3. Фоновые задания

Критичный сценарий: пользователь запустил проверку, обновил страницу или перешёл
между вкладками.

Проверить:

- задача остаётся в списке активных/последних проверок;
- прогресс продолжает обновляться;
- кнопку остановки можно нажать, задача переходит в `stopped`;
- параллельные задачи не запускаются бесконтрольно, лишние становятся в очередь;
- результат сохраняется в базу после завершения.

## 4. E2E fixture-сайты

Автоматически покрыто в `tests/test_e2e_scan_fixtures.py`:

- хороший сайт с footer-ссылками на политику, согласие, cookie policy и оферту;
- форма заявки с телефоном/email/name и чекбоксом согласия;
- встроенная форма-виджет без обычного `<form>`;
- трекер Google Tag Manager;
- cookie-баннер;
- soft-404/catch-all 200, где `/privacy` возвращает обычную оболочку сайта;
- полностью недоступный сайт.

Главный критерий: догадка `/privacy` не должна подавлять риск отсутствия
политики, если содержимое не похоже на юридический документ.

## 5. Реальные сайты для ручной регрессии

Перед продакшен-релизом прогнать 5-7 сайтов:

- сайт с документами в подвале;
- сайт на Tilda/конструкторе;
- клиника или медицинская запись;
- образовательный/детский проект;
- e-commerce с заказом/доставкой;
- сайт с cookie-баннером и аналитикой;
- сайт, который блокирует ботов или отдаёт нестабильные 403/timeout.

Для каждого зафиксировать:

- найденные страницы;
- найденные документы и URL;
- найденные формы;
- cookie/tracker-блок;
- 3 главных риска;
- PDF открывается и выглядит компактно.

## 6. LLM и стоимость

LLM не должен быть первым способом добычи фактов. Порядок:

1. детерминированный сбор страниц, ссылок, форм, документов, cookie/tracker;
2. эвристический чек-лист по документам;
3. LLM-анализ только укороченного текста документа;
4. LLM-агент сайта только если ключевые документы не найдены;
5. все выводы LLM перепроверяются фактической загрузкой URL/цитатами.

Сценарии:

- LLM выключен: отчёт всё равно создаётся;
- ключ неверный или API недоступен: приложение не падает, ставит ручную проверку;
- документ 40-100 тыс. символов: в LLM отправляется ограниченный фрагмент;
- агент предлагает URL: URL должен быть того же домена и реально похож на документ;
- LLM не может поставить `found` без цитаты.

## 7. PDF и коммерческий вид

Проверить:

- score в отчёте capped до `100 / 100`;
- нет запрещённых формулировок: «вы нарушаете закон», «штраф неизбежен»,
  «сайт незаконен»;
- блок ответственности помечен как справочный;
- отчёт не раздувается повтором чек-листов на каждый документ;
- видны основные цифры, топ-риски, рекомендации и пакеты услуг;
- пользовательские значения экранируются;
- PDF скачивается из интерфейса.

Автотесты: `tests/test_report_render.py`, `tests/test_pdf_quality_acceptance.py`.

## 8. База и история

Проверить:

- `DATABASE_URL` или persistent SQLite volume настроены;
- новые проверки сохраняются;
- история переживает перезапуск контейнера;
- статус лида меняется и сохраняется;
- PDF-путь сохраняется и файл доступен;
- массовые результаты экспортируются в XLSX/ZIP.

## 9. Ошибки сайтов

Сценарии:

- DNS error;
- connection refused;
- timeout;
- TLS error;
- 403/429;
- 404 на типовых путях;
- redirect на другой домен;
- пустой PDF или PDF без извлекаемого текста;
- DOCX/PDF больше лимита скачивания.

Ожидание: приложение не падает, сохраняет ошибку в `result.errors`, помечает
`requires_manual_review=True`.

## 10. Railway/production

Перед деплоем:

- Docker image собирается;
- Streamlit слушает `0.0.0.0:$PORT`;
- Chromium установлен, Playwright запускается headless;
- env-переменные заданы;
- persistent storage или PostgreSQL подключены;
- PDF создаётся внутри контейнера;
- логи показывают ошибки сканирования, но не секреты.

Команды:

```bash
docker build -t legal-audit-tool .
docker run -p 8501:8501 --env-file .env legal-audit-tool
```

## Критерии готовности перед обновлением production

- `scripts/run_acceptance.py --full` проходит;
- одна ручная проверка реального сайта завершается;
- PDF открывается;
- история сохраняется после перезапуска;
- LLM либо работает, либо корректно отключается без падения;
- отчёт содержит только аккуратные формулировки о признаках риска.
